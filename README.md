# ESS 배터리 수명 예측

초기 100사이클의 측정값으로 배터리가 총 몇 사이클까지 사용할 수 있는지 예측하는 회귀 프로젝트다. 초기 방전 용량이 비슷한 셀이라도 최종 수명은 다를 수 있다는 점에서 출발했다. 용량 자체뿐 아니라 초기 사이클 사이의 변화가 수명을 구분하는 데 도움이 되는지 확인하고자 했다.

Batch 1 내부 검증에서는 ΔQ 로그분산 하나를 사용한 선형회귀의 오차가 가장 작았다. 그러나 Batch 2에서는 MAPE가 26.175%로 높아졌고, 대부분의 셀을 실제보다 오래 사용할 수 있다고 예측했다. 이 차이를 중심으로 피처 선택과 검증 방식, 실제 ESS 적용의 한계를 정리했다.

## 프로젝트 개요

- 데이터셋: MIT–Stanford Battery Dataset, Severson et al. (2019)
- 학습 데이터: Batch 1, `2017-05-12`
- 평가 데이터: Batch 2, `2018-02-20`
- 태스크: **Regression — 초기 100사이클로 총 Cycle Life 예측**
- 타깃: 원본 수명을 점검하고 보정한 `cycle_life_model`
- 평가 지표: MAPE(%), 보조 지표 RMSE(사이클)
- Batch 3는 DAY1 EDA에서 비교했으며, DAY2 추가 모델 평가는 진행하지 않았다.

장·단수명 두 범주로 나누기보다 셀별 수명 차이를 연속적인 값으로 확인하기 위해 회귀를 선택했다. 예측 대상은 총 수명이며, 현재 사용 시점에서 얼마나 더 쓸 수 있는지를 뜻하는 잔여수명(RUL)과는 구분한다.

## EDA

DAY1의 수명 통계와 상관계수는 **원본 제공 수명 기준**이다. Batch 1은 46셀을 탐색했고, DAY2에서 수명 보정과 미완료 셀 제외를 거쳐 모델링 대상이 41셀이 됐다.

### Cycle Life 분포

Batch 1은 500~1000사이클의 중간 수명 셀이 78.3%였고, 500사이클 미만의 단수명 셀은 없었다. 반면 Batch 2에서는 수명이 확인된 39셀 중 28셀(71.8%)이 단수명이었다. Batch 3는 1000사이클을 넘는 장수명 비율이 52.3%로 가장 높았다.

같은 데이터셋에 속하더라도 배치마다 예측할 대상의 구성이 달랐다. 따라서 Batch 1에서 검증 점수가 잘 나오는 것과 Batch 2에서도 잘 예측하는 것은 따로 확인해야 한다고 판단했다. 짧은 수명이라는 이유만으로 Batch 2의 셀을 이상치로 제거하지 않았다.

### 열화 곡선

일부 셀은 용량이 완만하게 줄다가 후기 구간에서 감소 속도가 빨라졌다. Batch 2에서는 이런 변화가 비교적 이른 사이클에 나타나는 셀이 많았다. 기울기가 달라지는 구간을 knee 후보로 관찰했지만, 자동으로 knee를 검출하거나 발생 시점을 수치로 추정하지는 않았다.

한편 Batch 1의 일부 셀은 마지막 기록에서도 용량이 충분히 남아 있었다. 이를 보면서 파일의 마지막 사이클을 곧바로 수명 종료로 받아들이면 안 된다고 판단했고, 모델링 전에 라벨을 다시 점검했다. 전체 열화 곡선은 이 점검에 사용했으며 초기 수명 예측 모델의 입력에는 넣지 않았다.

### ΔQ(V) 곡선

`ΔQ(V) = Q100(V) − Q10(V)`로 초기 방전 곡선의 변화를 계산했다. 세 배치 모두 ΔQ 로그분산이 작을수록 수명이 긴 경향을 보였다. Batch 1에서 수명과의 Spearman 상관계수는 −0.871이었다.

10사이클의 방전 용량 자체는 수명과의 관계가 약했다. 초기 용량이 얼마나 큰지보다 **초기 두 시점 사이에서 곡선이 어떻게 달라졌는지**가 더 유용한 신호일 수 있다고 보았고, ΔQ 로그분산을 단일 피처 기준 모델에 사용했다.

### 충전 조건과 수명

Batch 1에서는 1단계 C-rate가 높을수록 수명이 짧아지는 경향이 있었지만, 다른 배치에서는 관계가 약했다. 같은 초기 C-rate라도 전환 SOC와 이후 충전 조건에 따라 수명이 달랐다. 프로토콜별 표본도 적어 특정 C-rate를 최적 조건으로 정하지 않았다.

충전 시간과 수명의 상관은 Batch 1에서 양수(ρ=0.638), Batch 2에서 음수(ρ=−0.809)였다. 한 배치에서 상관이 높다는 이유만으로 유용한 입력이라고 확정하기 어렵다고 보았고, 보조 피처의 효과는 Batch 1 내부 검증에서 비교했다.

### 피처 간 중복

ΔQ 평균과 최솟값의 Pearson 상관은 0.993, 용량 변화량과 초기 감소율은 −0.979, 평균 온도와 최고 온도는 0.960이었다. 서로 비슷한 정보를 담은 변수가 많았다. 13개를 모두 입력하기보다 대표 피처로 조합을 만들고, Ridge와 Elastic Net도 함께 비교했다.

## Modeling

### 타깃 점검

Batch 1의 셀 0~4는 후속 실험의 최종 수명을 반영했다. 셀 8·10·12·13·22는 저자 공개 코드에서 미완료로 처리한 셀이므로 일반적인 수명 회귀 대상에서 제외했다. Batch 2에서는 정답 수명이 없는 8셀을 제외했다.

| 데이터 | 원본 셀 수 | 처리 | 모델링 셀 수 |
|---|---:|---|---:|
| Batch 1 | 46 | 5셀 수명 보정, 별도의 미완료 5셀 제외 | 41 |
| Batch 2 | 47 | 수명 결측 8셀 제외 | 39 |

원본 `cycle_life`를 덮어쓰지 않고 `cycle_life_model`을 따로 만들었다. 보정값과 제외 사유, 출처는 [label_audit.csv](data/processed/features_20261002_125401_694125/label_audit.csv)에 남겼다. 후속 실험의 전체 곡선을 재구성한 것은 아니며, 현재 과제의 Batch 2를 Batch 1에 이어 붙이지 않았다.

### 피처 엔지니어링 전략

초기 10~100사이클의 용량·온도·내부 저항·충전 시간, ΔQ 통계, 충전 설정에서 13개 후보를 추출했다. 최종 모델링 대상 80셀에는 후보 피처의 결측이 없었다. 셀 ID, barcode, 배치명과 전체 수명 기록은 입력에서 제외했다.

| 조합 | 사용 피처 | 확인하려는 내용 |
|---|---|---|
| `dq_only` — 1개 | `delta_q_log_var` | EDA의 핵심 신호 하나로 어느 정도 예측할 수 있는가 |
| `measurement` — 5개 | 위 피처 + `qd_change_100_10`, `tavg_median`, `chargetime_median`, `ir_median` | 초기 상태 정보를 더하면 오차가 줄어드는가 |
| `plus_charge` — 8개 | 위 5개 + `charge_c1`, `charge_c2`, `switch_soc` | 충전 설정이 추가 설명력을 주는가 |

각 후보의 정의는 [feature_dictionary.csv](data/processed/features_20261002_125401_694125/feature_dictionary.csv)에 정리했다. 로그 타깃 모델은 `log10(cycle_life_model)`을 학습하고, 예측을 사이클 단위로 되돌린 뒤 지표를 계산했다.

### 데이터 분할

같은 충전 프로토콜의 셀이 학습과 검증에 나뉘면 익숙한 조건에 대한 성능을 확인하게 될 수 있다. 이번에는 **학습하지 않은 충전 조건에서도 예측이 되는지**를 보고 싶어 프로토콜 단위로 분리했다. 단순히 hold-out을 사용했다는 사실보다 그룹이 실제로 겹치지 않는지를 확인했다.

| 구분 | 셀 수 | 프로토콜 수 | 용도 |
|---|---:|---:|---|
| Batch 1 train | 31 | 17 | 그룹 5-fold CV로 후보 비교 |
| Batch 1 hold-out | 10 | 5 | 선택 후보의 별도 검증 |
| Batch 2 test | 39 | 12 | 최종 평가 |

Batch 1의 train과 hold-out 사이, 각 CV 학습·검증 폴드 사이에 공통 프로토콜이 없도록 확인했다. 무작위 hold-out의 seed는 42다. Ridge와 Elastic Net의 규제 강도는 바깥 CV 학습 폴드 안에서 그룹 3-fold로 선택했고, 표준화도 각 학습 폴드에서만 수행했다.

### 모델 선택 및 근거

중앙값 Dummy, 원타깃·로그타깃 선형회귀, Ridge, Elastic Net을 비교했다. 피처 조합까지 합하면 후보는 9개다.

| 모델 | 피처 조합 | CV 평균 MAPE (%) |
|---|---|---:|
| **Linear_log10** | **dq_only** | **10.178** |
| Ridge_log10 | dq_only | 10.198 |
| ElasticNet_log10 | dq_only | 10.431 |
| ElasticNet_log10 | plus_charge | 11.384 |
| ElasticNet_log10 | measurement | 12.547 |
| Ridge_log10 | measurement | 13.282 |
| Ridge_log10 | plus_charge | 13.469 |
| Linear_raw | dq_only | 13.756 |
| Dummy_median | 입력 피처 없음 | 24.183 |

최종 선택은 **ΔQ 로그분산 단독 로그타깃 선형회귀**다. CV 오차가 가장 작았고, 단일 피처 Ridge와의 차이는 0.020%p로 작아 더 단순한 설정을 유지했다. 선형회귀가 통계적으로 우월하다고 판단한 것은 아니다.

이번 비교에서 눈에 띈 점은 변수를 늘리는 것이 성능 개선으로 바로 이어지지 않았다는 것이다. 다만 Elastic Net에서는 충전 설정을 추가하면서 12.547%에서 11.384%로 개선됐으므로, 충전 정보가 쓸모없다고 결론 내릴 수는 없다. 현재 표본과 후보 범위에서는 추가 변수의 이점이 단일 피처 모델을 넘어설 만큼 크지 않았다고 해석했다.

선택한 모델을 31셀로 학습해 hold-out에서 확인한 뒤, 모델 종류와 피처를 유지한 채 Batch 1 전체 41셀로 재학습했다. 이 모델로 Batch 2를 최종 평가했다.

## 성능 결과

| 구분 | MAPE (%) | 비고 |
|---|---:|---|
| Train (Batch 1 CV) | 10.178 | 31셀의 그룹 5-fold 검증 평균; 각 폴드 학습 24~25셀 |
| Valid (Batch 1 Hold-out) | 9.146 | 학습 31셀, 검증 10셀 |
| Test (Batch 2) | 26.175 | Batch 1 전체 41셀 재학습, Batch 2 39셀 평가 |
| Gap (Train-Valid) | −1.032 | Valid − Train, 단위 %p |
| Gap (Valid-Test) | +17.029 | Test − Valid, 단위 %p |
| Gap (Target-Test) | +17.075 | Test − 9.1%, 단위 %p |

과제의 행 이름을 유지하되 Gap은 **양수일 때 기준보다 오차가 커진 것**으로 계산했다. Train은 학습 데이터에 직접 맞춰 얻은 점수가 아니라 CV 검증 평균이다. 따라서 첫 번째 Gap이 음수라는 사실만으로 과적합이 없다고 판단하지 않는다.

논문 참고 MAPE 9.1%에는 도달하지 못했다. Hold-out은 9.146%로 비슷했지만, 과제에서 논문과 비교할 대상은 Batch 2 Test의 26.175%다. 또 데이터 구성과 전처리·분할·피처가 달라 논문을 동일 조건으로 재현한 결과는 아니다.

RMSE는 CV 폴드 평균 117.864, hold-out 212.015, Test 170.525사이클이었다. Test에서 RMSE는 hold-out보다 낮아졌지만 MAPE는 높아졌다. 같은 100사이클 오차도 실제 수명 500사이클에서는 20%, 2000사이클에서는 5%이므로, 짧은 수명이 많은 평가에서는 상대오차를 함께 봐야 한다.

최종 표는 [model_performance.csv](results/model_performance.csv)에 저장했다.

## 오류 분석

Batch 2에서는 **39셀 중 38셀(97.4%)의 수명을 과대 예측**했다. 평균 오차가 커진 것에 더해, 예측이 한쪽 방향으로 치우쳤다는 점을 중요하게 보았다.

| 실제 수명 구간 | 셀 수 | MAPE (%) | 과대 예측 셀 수 |
|---|---:|---:|---:|
| 500사이클 미만 | 28 | 26.496 | 28 |
| 500~1000사이클 | 8 | 31.508 | 8 |
| 1000사이클 초과 | 3 | 8.952 | 2 |

상대오차가 가장 큰 Batch 2 Cell 18은 실제 449사이클을 730.479사이클로 예측했다(APE 62.690%). 단수명뿐 아니라 중간 수명 셀도 모두 과대 예측했다. 장수명 구간의 오차는 작았지만 3셀뿐이어서 장수명 예측이 안정적이라고 보기는 어렵다.

상대오차 상위 3셀인 Cell 18·6·15는 모두 실제 수명이 500사이클 미만이었고 과대 예측됐다. 그중 Cell 6·15는 `3.6C(9%)-5C` 프로토콜을 공유했지만 Cell 18은 다른 조건이었다. 짧은 수명에서 큰 상대오차가 나타난 공통점은 확인할 수 있었지만, 특정 충전 조건 하나를 원인으로 지목할 근거는 부족했다.

Hold-out에서는 반대로 10셀 중 8셀을 과소 예측했다. 특히 Cell 2의 실제 수명 2237사이클을 1631.156사이클로 예측해 약 606사이클의 차이가 났다. 같은 프로토콜인 Cell 0·1·2의 수명 순서도 예측값이 재현하지 못했다. ΔQ 하나로 전체 경향을 잡을 수 있어도 개별 셀의 차이까지 설명하기에는 부족한 사례다.

배치마다 수명 분포와 피처–수명 관계가 달라지는 점, 작은 학습 표본은 성능 차이의 원인 후보다. 다만 최종 재학습에서 학습 셀 수도 31개에서 41개로 늘었으므로, 오차 방향 변화의 원인을 배치 차이 하나로 단정하지 않았다. 다음 실험에서는 더 다양한 조건의 학습 자료를 확보하고, 새로운 독립 평가 자료에서 이런 가설을 확인할 필요가 있다. 이번 Test 결과를 보고 재튜닝하거나 오차가 큰 셀을 제외하지는 않았다.

## ESS 도메인 해석

이 모델은 초기 시험을 마친 셀의 예상 수명을 비교하고, 추가 시험이 필요한 셀을 정하는 데 보조 정보로 활용할 수 있다. 충분한 검증을 거친다면 셀 선별이나 교체 계획의 참고값으로도 검토할 수 있다.

내가 가장 주의해서 본 부분은 수명을 실제보다 길게 예측하는 경우다. 이 예측을 그대로 교체 일정에 사용하면 실제보다 늦게 교체를 계획할 수 있다. 따라서 운영에 적용할 때는 평균 MAPE를 낮추는 것뿐 아니라 과대 예측이 얼마나 자주, 얼마나 크게 발생하는지도 판단 기준에 넣어야 한다고 생각한다.

현재 결과는 실험실 셀의 총 수명 예측이다. 실제 BESS의 팩 구성, 온도, 충방전 패턴과 센서 조건에서는 검증하지 않았고, 교체 시점이나 안전성을 직접 판단하는 모델도 아니다. 배포 전에는 운영 조건을 반영한 데이터와 별도 Live Test, 예측 불확실성 평가가 필요하다. 허용할 오차 수준도 운영 목적에 맞게 정해야 한다.

이번 분석에서 얻은 결론은 ΔQ가 수명과 연관된 신호라는 점과, 그 관계만으로 다른 배치의 수명을 정확히 예측할 수는 없다는 점이다. 피처의 상관을 확인하는 단계와 새로운 데이터에 적용할 수 있는지 검증하는 단계를 구분해야 했다.

## 트러블슈팅

### barcode가 깨지거나 두 배치에서 46개가 같다고 나온 문제

처음에는 barcode가 쉼표·기호 등으로 출력됐고, Batch 1·2에서 46개가 공통으로 나타났다. 문자열이 저장된 위치를 가리키는 MATLAB 객체 정보를 실제 문자 코드로 잘못 읽은 것이 원인이었다.

02에서 `#subsystem#/MCOS`의 참조를 따라 실제 문자열을 찾도록 수정했다. 수정 후 Batch 1은 46개, Batch 2는 47개의 barcode가 정상적으로 읽혔고 배치 내부와 두 배치 사이의 중복은 0개였다. 처음 나온 46개 일치는 동일 셀의 증거로 사용하지 않았다. 이 해독 코드는 이번 MAT의 저장 형식을 확인하도록 작성했으며, 형식이 다른 파일은 별도 확인이 필요하다.

### 마지막 기록과 수명값이 맞지 않는 문제

Batch 1의 원본 수명은 마지막 기록 사이클보다 1 컸지만, 일부 셀은 기록 종료 시점에도 초기 용량의 약 95%를 유지했다. 단순한 숫자 차이로 끝내지 않고 후속 실험과 미완료 셀 여부를 확인했다. 그 결과 위의 타깃 점검 기준을 적용했다. 종료 용량 비율만 보고 모든 셀의 수명을 임의로 바꾸지는 않았다.

### 충전 프로토콜 8개를 숫자로 변환하지 못한 문제

Batch 2의 `VarCharge`, `SLOWCYCLE` 표기는 일반적인 2단계 충전 형식과 달라 현재 규칙으로 해석되지 않았다. 임의의 C-rate나 SOC를 채우지 않고 원문과 처리 사유를 남겼다. 이 8셀은 수명 타깃도 결측이었으므로 회귀 대상에서 제외했다. 단순히 파싱이 안 된다는 이유로 평가 가능한 셀을 버린 것은 아니다.

### `GroupShuffleSplit`, `sys`의 `NameError`

분할과 환경 기록 코드를 실행할 때 import가 빠져 오류가 발생했다. 현재는 03의 상단 라이브러리 셀에 필요한 import를 모았다. 커널을 새로 시작했거나 셀을 건너뛰었다면 상단부터 다시 실행해야 한다. `df_train`, `FINAL_DIR` 같은 변수도 앞선 셀에서 만들어지므로 마지막 셀만 단독으로 실행할 수는 없다.

### 다른 환경에서 실행할 때 확인할 부분

| 증상 | 확인할 내용 |
|---|---|
| 설치했는데 `ModuleNotFoundError` 발생 | VS Code의 커널이 설치에 사용한 `.venv`인지 확인한다. 노트북에서 `import sys; print(sys.executable)`로 경로를 확인할 수 있다. |
| MAT 파일을 찾지 못함 | 원본은 Git 제외 대상이다. `data/README.md`의 파일명과 `data/raw/` 위치, 현재 작업 경로를 확인한다. |

| 새 피처를 만들었는데 03이 이전 데이터를 사용함 | 03의 `SNAPSHOT_DIR`을 새 폴더로 바꾼다. 최신 폴더를 자동 선택하는 구조가 아니다. |
| CSV 해시·셀 수 검증에서 중단됨 | 피처 CSV와 `metadata.json`이 같은 실행에서 생성된 묶음인지 확인한다. 검증문을 지우지 말고 파일 조합과 변경 여부를 먼저 확인한다. |
